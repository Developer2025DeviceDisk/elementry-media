# Product brands

The homepage and product catalog share the 43 store-supplied brands and product lines in `Frontend/src/lib/constants/brands.ts`. Each entry retains the supplied display name and official website URL. Update that file to maintain the directory and selector together. The directory describes the range supplied by the store; it does not create product records or assert authorized dealership status.

`products.brand` is an optional MongoDB string, 1–100 characters. Existing documents without it remain valid and visible in the unfiltered catalog. Set the actual brand on each product, using a directory name such as `Panasonic`, `Yamaha (Pro Audio)` or `RØDE`, to include that product in the corresponding filter. Do not infer brands from ambiguous names or SKUs. For example, after identifying a real product by its SKU, update it in Atlas with `{ $set: { brand: 'Panasonic', updatedAt: new Date() } }`. No existing products are automatically reassigned.

Deploy the additive validator with `npm run db:setup` in Backend and restart the API after code changes. Brand is returned in catalog, detail and wishlist responses when stored. Legacy JSON imports may include an optional `brand` field. Catalog caches expire after `CACHE_TTL_SECONDS`; after changing a product in Atlas, allow that TTL for cached responses to refresh.

`GET /api/v1/products?page=1&limit=12&brand=Panasonic&q=camera` combines an exact, case-insensitive brand match with the existing literal text search. Both query fields allow at most 100 characters; regular expression punctuation is escaped. Inactive products are excluded. Missing or blank `brand` means all brands. Pagination and cache keys retain the brand and search together.

The basic brand filter works independently of `NEXT_PUBLIC_SEARCH_API_ENABLED`. Product cards show the stored brand. Detail pages link back to that brand's catalog and offer its official website when listed in the directory. Filtered pages with no matching inventory display an empty state and a contact link.
